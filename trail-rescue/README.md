# 越野赛事保障系统（Trail Rescue）

绑定选手 **GPS 定位** 与 **检录（打卡）** 数据，实时做赛道匹配；当选手
**进入危险路段** 或出现 **配速/运动异常** 时，自动呼叫最近的救护点，
并对超时未确认的派单自动升级、呼叫带 AED 的备援点。

纯 Python 3.11 标准库实现，**零第三方依赖**，可离线运行。

---

## 一、它做什么

```
GPS 定位流 ──┐
             ├─ 赛道折线匹配（里程/海拔/横向偏离/危险路段）
检录打卡流 ──┘    │
                  ├─ 运动分析（滑窗配速 / 停滞 / 异常跳点）
                  ├─ 检录校验（顺序 / 漏检 / 关门）
                  └─ 风险判定
                        ├── 进入危险路段（警戒 / 危急两级）
                        ├── 危险路段内停滞（危急）
                        ├── 配速异常偏慢 / 偏快
                        ├── 偏离赛道
                        ├── 漏检 / 超关门
                        └── GPS 失联 / 发枪未出现
                              │
                              ▼
                    自动呼叫最近「开放中」救护点
                    （直线距离 + ETA + AED 匹配）
                              │
                    5 分钟未确认 → 升级危急
                    → 自动改派下一近的备援点（携带 AED）
```

### 派单防误报 / 防重复（关键工程规则）

- **危险路段 ≠ 人人报警**：进入路段先记录监视；正常配速穿越不派单，
  只有在路段内 **停滞 / 配速异常 / 偏航** 时才自动呼叫。
  `critical` 路段（断崖刃脊）的异常直接是危急级别。
- **一人一车**：同一选手已有未结派单时，后续告警（如路段内又检测到停滞）
  合并到同一处置单，不重复派救护车；处置动作（接单/到场/解除）整组同步。
- **短时复发抑制**：刚由救护点处置解除的同类问题（如收容下撤途中再次
  报配速慢），15 分钟内不再重复派车。
- **派单冷却**：每类风险有独立冷却窗口，避免 GPS 抖动刷告警。
- **只移动过才谈停滞**：开赛集结原地不动不计停滞；真正走过一段后停下
  才开始计时（默认 180 秒）。

## 二、快速开始

```bash
cd trail-rescue

# 1) 离线跑一遍内置赛事剧本（5 名选手，含全部异常场景），打印事件流+总结
python3 -m trail_rescue sim

# 2) 启动指挥大屏
python3 -m trail_rescue serve --port 8080
# 打开 http://localhost:8080 ，点「▶ 开始仿真」（30×~300× 倍速可调）

# 3) 运行全部 15 个单元测试
python3 -m unittest discover -s tests
```

## 三、内置剧本（`trail_rescue/simulation.py`）

一条 8.6 km、海拔 2400–3450m 的高海拔山地赛道，5 个救护点、
6 个检录点、2 个危险路段：

| 号码 | 选手 | 剧本 | 系统动作 |
|---|---|---|---|
| 101 | 张岚 | 正常完赛 | 穿危险路段仅监视，不派单 |
| 102 | 李彻 | 落石峡谷前突然减速 | pace_slow 派单，首派超时 → 升级改派 |
| 103 | 王屿 | 断崖刃脊内受伤停滞 5 分钟 | 危急呼叫，首派无 AED 的垭口点 5 分钟未确认 → 升级改派海子边点（AED），担架下撤 |
| 104 | 赵菁 | 全程 16.7 分/公里（疑似抽筋/失温） | 多次风险合并为连续医疗跟进，最终强制收容 |
| 105 | 周沐 | 偏离赛道 260m + CP3 漏打卡 | 偏航派单引导返回 + 漏检危急核实（设备故障补录） |

## 四、HTTP 接口（真实设备网关也用同一套 API）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/state` | 完整态势：赛道/危险区/检录点/救护点/选手/告警 |
| POST | `/api/track` | `{bib, lat, lon, ele?, speed?, ts?}` 上报定位 |
| POST | `/api/checkin` | `{bib, checkpoint_id, ts?}` 上报检录 |
| POST | `/api/alerts/<id>/ack` | 救护点接单确认 |
| POST | `/api/alerts/<id>/onscene` | 到达现场 |
| POST | `/api/alerts/<id>/resolve` | `{resolution}` 处置解除 |
| POST | `/api/sim` | `{action: start|pause|reset, speed}` 仿真控制 |
| GET | `/api/events` | SSE 实时事件流（大屏用） |

### 接入真实设备

仿真只是一个数据生产器；`Engine` 与仿真完全解耦。真实部署时把设备网关
收到的定位/检录 POST 到 `/api/track`、`/api/checkin` 即可，告警、派单、
大屏全部复用：

```bash
curl -X POST localhost:8080/api/track -d '{
  "bib":"103","lat":31.1351,"lon":103.3273,"speed":0.2}'
```

## 五、代码结构

```
trail_rescue/
├── geo.py          # haversine / 局部等距圆柱投影 / 点到线段投影
├── models.py       # 赛道/危险路段/检录点/救护点/选手/告警/派单
├── motion.py       # 滑窗配速、停滞、异常速度参数
├── engine.py       # 核心：定位+检录绑定、风险判定、自动派单、超时升级
├── simulation.py   # 赛道与 5 人剧本、时钟可外部推进的仿真器
├── storage.py      # JSONL 事件日志 + 原子写快照（无数据库）
├── server.py       # 标准库 HTTP：REST + SSE + 静态文件 + 仿真线程
├── cli.py          # sim / serve / test 命令
└── web/            # 指挥大屏（原生 HTML/CSS/JS，Canvas 画地图，无 CDN）
tests/
└── test_engine.py  # 15 个测试：地理计算/各类告警/派单升级/漏检/失联/快照
```

### 判定阈值（`engine.py` / `motion.py`，按赛事可调）

| 参数 | 默认 | 含义 |
|---|---|---|
| `OFF_COURSE_M` | 200 m | 偏离赛道告警距离 |
| `STATIONARY_SECONDS` | 180 s | 停滞判定时长 |
| `STATIONARY_SPEED_MS` | 0.55 m/s | 低速门限 |
| `SPEED_SPIKE_MS` | 8.3 m/s | 瞬时速度异常（约 3:20/km） |
| `PACE_WINDOW_SEC` | 240 s | 配速滑动窗口 |
| `STALE_GPS_SEC` | 300 s | 定位失联判定 |
| `ACK_TIMEOUT_SEC` | 300 s | 派单未确认升级超时 |
| 危险路段 `buffer_m` | 100–120 m | 路段两侧有效缓冲带 |
| `PaceBand` | 按赛段 | 各赛段合理配速上下限（分/公里） |

## 六、数据与恢复

- `data/events.jsonl`：全部状态事件追加日志（可审计、可回放）。
- `data/snapshot.json`：每次告警状态变化原子落盘的引擎快照。
- 进程重启后可恢复选手位置/检录/告警/派单与冷却状态。
